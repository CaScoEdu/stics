In this lesson, we transform the map from
 a simple graphical representation into a real travel network:
- buildings become nodes in a
  [graph](https://en.wikipedia.org/wiki/Graph_(discrete_mathematics)),
- pedestrian paths become weighted edges, and
- the browser automatically calculates the shortest route
   between two points using [Dijkstra's algorithm](https://en.wikipedia.org/wiki/Dijkstra%27s_algorithm).
    
 <AsideTip title="Final output">
The final result is an interactive navigation experience, with buildings highlighted and an animated line following the selected route.
</AsideTip>

## Define the Graph with Junctions (`grafo.json`)
Now that we have positioned the road junctions in `mappa.svg`, we need to update `grafo.json`. Connections will no longer link buildings directly; they will pass through junction nodes.

<Aside type="tip" title="Recap: undirected and weighted graphs">
- **Undirected**: Connections ([edges](https://en.wikipedia.org/wiki/Graph_(discrete_mathematics))) are bidirectional. If junction `A` is connected to junction `B` with a certain weight, the same cost applies in both directions.
- **Weighted**: Each edge has a numerical cost (the weight, e.g. meters or seconds), used by **Dijkstra** to calculate the shortest path.
</Aside>

Here is a valid `grafo.json` snippet modeling the route from the offices to the intersections via junctions:

```json title="grafo.json"
{
  "edificio-uffici": {
    "snodo-uffici": 30
  },
  "snodo-uffici": {
    "edificio-uffici": 30,
    "snodo-incrocio-ovest": 100
  },
  "snodo-incrocio-ovest": {
    "snodo-uffici": 100,
    "snodo-aule": 100,
    "snodo-mensa": 100
  }
}
```

### How is `grafo.json` structured?
This file represents the campus road and connection graph using a nested `JSON` object (an adjacency map or table):

- **Top-level keys (nodes)**: Each top-level key (such as `"edificio-uffici"` or `"snodo-incrocio-ovest"`) represents a reference point on the map, whether a building or a strategic intersection.

- **Nested objects (edges and weights)**: Each node contains another object listing its directly reachable neighbors and their numerical weights (the distance in meters or travel cost) required to move from one point to another.

- **Bidirectionality**: Notice that connections are mirrored (e.g. from `edificio-uffici` to `snodo-uffici` and back), reflecting the undirected graph structure in which roads can be traveled in either direction.

<Aside type="tip" title="📏 From estimated weight to exact geometric distance">

In the early stages of graph modeling, using fixed, approximate values (such as **100** for main routes and **30** for short connections to buildings) is an **extremely pragmatic and effective choice for teaching purposes**.

##### Why the approximate approach is "OK" for our purposes:
1. **Focus on the algorithm:** It lets students concentrate on how **Dijkstra** works and on the graph data structure (`grafo.json`), without being distracted by repetitive geometric calculations.
2. **Correct logical proportions:** For shortest-path calculations, what matters is not the actual unit of measurement (meters or kilometers), but the **cost relationship** between edges. Giving longer roads a higher weight and access paths a lower one still ensures that the algorithm chooses the right route.

##### How to calculate the actual distance in units (pixels)

For complete geometric accuracy, edge weights should correspond exactly to the pixel distance on the Cartesian plane of the SVG `viewBox` (`0 0 800 600`).

Because the paths on our map are **orthogonal** (moving only horizontally or vertically), calculating the distance between two nodes A and B is very simple and does not require complex formulas such as the Pythagorean theorem:

- **Horizontal movement:** The distance is the absolute difference between the `x` coordinates:
  `Distance = |x₂ - x₁|`

- **Vertical movement:** The distance is the absolute difference between the `y` coordinates:
  `Distance = |y₂ - y₁|`

*Example:* If a vertical road segment starts at `y = 80` and ends at `y = 220`, the exact edge weight in `grafo.json` is simply `|220 - 80| = 140` units.
</Aside>

## Competition and Collaboration
When several [**processes**](https://it.wikipedia.org/wiki/Processo_(informatica)) run in a computing system, they can interact in two main ways:

* **Competition**: Two or more processes need to
    exclusively use certain **limited resources** that are needed by both,
    and therefore compete to obtain them. For example, two processes attempting
    to write simultaneously to the same file.
* **Collaboration**: The processes do not compete, but must **coordinate**
    and **exchange information** to perform a common task (e.g., a
    *producer* process inserts data into a [**buffer**](https://it.wikipedia.org/wiki/Buffer), while a *consumer* process retrieves it).

In this lesson, we will focus on **competition**. **Collaboration** will be explored in a subsequent lesson on the Producer-Consumer problem.

<Aside type="caution" title="The risk of disorder">
In both cases, a **lack of coordination** can generate **serious errors**,
**unpredictable behavior**, or states of **severe data corruption**.
</Aside>

## Competition: [Shared Resource](https://it.wikipedia.org/wiki/Concorrenza_(informatica)), [Critical Section](https://it.wikipedia.org/wiki/Sezione_critica), and [Mutual Exclusion](https://it.wikipedia.org/wiki/Mutua_esclusione)
When processes **compete** for access to common elements (such as **global
variables**, **files**, or **data structures**), any reusable hardware or software
element contested by the processes is defined as a **shared resource**.

To avoid **conflicts**, a **critical section** is defined as the portion of
code within a process where the shared resource is accessed to
**read or modify it**.

### The Need for Mutual Exclusion
To preserve **data consistency** and avoid so-called [**race conditions**](https://it.wikipedia.org/wiki/Race_condition) (situations in which the execution order unpredictably alters the result), the system must guarantee [**mutual exclusion**](https://it.wikipedia.org/wiki/Mutua_esclusione):
* At any given moment, at most **one process** may be in its own
    critical section and use the shared resource.

## The Access Protocol (Request - Use - Release)
To guarantee **mutual exclusion** and ensure that each process obtains
access within **finite time**, access to a resource must strictly follow
a standard **protocol** structured in three phases:

<Steps>
1. **Resource request**: The process requests exclusive access to the
    resource (if it is occupied, it must wait).
2. **Resource use**: The process enters the critical section and
    performs the necessary operations on the resource.
3. **Resource release**: The process releases the resource, thereby allowing
    other waiting processes to acquire it.
</Steps>

## Practical Example: The [Stack](https://en.wikipedia.org/wiki/Stack_(abstract_data_type))

A classic example of a **shared data structure** subject to competition is the
**stack**, managed through an **array** and a **top pointer**
(`top`).

Operations such as **insertion** (`Push`) and **removal** (`Pop`) modify
simultaneously the same **shared variables** (`stack[]` and `top`). If these operations are executed concurrently without
adequate **synchronization**, there is a risk of **overwriting data** or reading
**undefined values** (*[race condition](https://en.wikipedia.org/wiki/Race_condition)*).

## The Risks of Synchronization: [Deadlock](https://en.wikipedia.org/wiki/Deadlock) and [Starvation](https://en.wikipedia.org/wiki/Starvation_(computer_science))

Managing **synchronization** and **resource waiting** can expose the
system to two important critical problems:

### Deadlock
A [**deadlock**](https://en.wikipedia.org/wiki/Deadlock) occurs when two or more processes become **permanently blocked** while waiting for a resource currently held by another process in the group.
* **Typical example**: Process `P1` **holds** resource `A` and requests `B`;
    process `P2` holds resource `B` and requests `A`. Neither process can
    continue.
* It is a blocking state from which the system cannot recover autonomously
    without external intervention (such as restarting or forcibly terminating
    the processes).

### Starvation
[**Starvation**](https://en.wikipedia.org/wiki/Starvation_(computer_science)) occurs when a process **can never access** a resource because it is continuously assigned to other processes (for example, because of **unbalanced priority policies**).
* Unlike a deadlock, **it is not a permanent condition**: the process
    is not blocked permanently, but simply waits
    indefinitely until the allocation policy grants it
    access.

## Summary

<KeyConcepts title="Key concepts">
- [**Concurrency**](https://en.wikipedia.org/wiki/Concurrency_(computer_science)): execution of multiple processes in **overlapping time intervals**.
- [**Shared resource**](https://en.wikipedia.org/wiki/Concurrency_(computer_science)): a resource usable by multiple processes.
- [**Critical section**](https://en.wikipedia.org/wiki/Critical_section): the part of code that accesses a shared resource.
- [**Mutual exclusion**](https://en.wikipedia.org/wiki/Mutual_exclusion): allows only one process at a time to access the shared resource.
- [**Race condition**](https://en.wikipedia.org/wiki/Race_condition): a situation in which the result depends on the order of concurrent operations.
- [**Deadlock**](https://en.wikipedia.org/wiki/Deadlock): mutually blocked processes waiting for resources held by each other.
- [**Starvation**](https://en.wikipedia.org/wiki/Starvation_(computer_science)): indefinite waiting by a process that is not assigned a resource.
</KeyConcepts>

Which property guarantees **mutual exclusion**?

- [x] At most one process at a time can access the shared resource in its critical section.
    > Correct: this prevents concurrent accesses from compromising data consistency.
- [ ] All processes access the resource simultaneously.
- [ ] A waiting process always obtains the resource within a finite time.
    > This is a progress guarantee, not the definition of mutual exclusion.

<Quiz id="quiz-deadlock-starvation">
Which situation describes a **deadlock**?

- [x] Two processes each wait for a resource held by the other and neither can continue.
    > Correct: the processes are blocked in mutual waiting.
- [ ] A process waits a long time because the resource is continuously assigned to others.
    > This is starvation: the process is disadvantaged but is not necessarily blocked mutually.
- [ ] Two processes access the same resource sequentially.
</Quiz>

<Quiz id="quiz-protocollo-accesso">
What is the correct order of the phases in the shared-resource access protocol?

- [ ] Use, request, release.
- [x] Request, use, release.
    > Correct: the process requests the resource, uses it in the critical section, and finally releases it.
- [ ] Release, use, request.
</Quiz>

<Quiz id="quiz-starvation">
What characterizes **starvation**?

- [ ] Two processes remain blocked because each waits for a resource held by the other.
    > This situation is a deadlock.
- [x] A process remains indefinitely waiting because the resource is continuously assigned to others.
    > Correct: the process does not obtain the resource, for example because of an unbalanced priority policy.
- [ ] Multiple processes access the same resource simultaneously without coordination.
    > This can cause a race condition.
</Quiz>

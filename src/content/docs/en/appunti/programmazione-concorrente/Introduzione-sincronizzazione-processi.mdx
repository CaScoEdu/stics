## ⚔️ Competition and 🤝 Cooperation
When multiple [**processes**](https://it.wikipedia.org/wiki/Processo_(informatica)) run in a computer system, they can interact in two main ways:

* **⚔️ Competition**: Two or more processes need exclusive access to **limited resources** that they both require, and therefore compete to acquire them. For example, two processes might try to write to the same file at the same time.
* **🤝 Cooperation**: Processes do not compete, but must **coordinate** and **exchange information** to perform a common task (e.g., a *producer* process that adds data to a [**buffer**](https://it.wikipedia.org/wiki/Buffer) and a *consumer* process that retrieves it).

In this lesson, we will focus on **competition**. **Cooperation** will be covered in a later lesson on the Producer–Consumer problem.

<Aside type="caution" title="The risk of disorder">
In both cases, a **lack of coordination** can lead to **serious errors**,
**unpredictable behavior**, or **severe data corruption**.
</Aside>

## ⚔️ Competition: [Shared Resources](https://it.wikipedia.org/wiki/Concorrenza_(informatica)), [Critical Sections](https://it.wikipedia.org/wiki/Sezione_critica), and [Mutual Exclusion](https://it.wikipedia.org/wiki/Mutua_esclusione)
When processes **compete** for access to common elements (such as **global variables**,
**files**, or **data structures**), any reusable hardware or software element contested by processes is called a **shared resource**.

To avoid **conflicts**, a **critical section** is the part of a process's code that accesses a shared resource to **read or modify it**.

### 🔒 The Need for Mutual Exclusion
To preserve **data consistency** and prevent [**race conditions**](https://it.wikipedia.org/wiki/Race_condition) (situations where the execution order unpredictably changes the result), the system must guarantee [**mutual exclusion**](https://it.wikipedia.org/wiki/Mutua_esclusione):
* At any moment, **at most one process** can be in its critical section and use the shared resource.

## The Access Protocol (Request–Use–Release)
To guarantee **mutual exclusion** and ensure that every process gains access in a **finite amount of time**, resource access must strictly follow a **standard protocol** with three phases:

<Steps>
1. **Request the resource**: The process requests exclusive access to the resource (if it is occupied, it must wait).
2. **Use the resource**: The process enters its critical section and performs the required operations on the resource.
3. **Release the resource**: The process releases the resource, allowing other waiting processes to acquire it.
</Steps>

## Practical Example: The [Stack](https://it.wikipedia.org/wiki/Pila_(informatica))

A classic example of a **shared data structure** subject to competition is a
**stack**, implemented using an **array** and a **top pointer** (`top`).

Operations such as **push** and **pop** modify the same **shared variables** (`stack[]` and `top`). If these operations run concurrently without proper **synchronization**, they may **overwrite data** or read **undefined values** (*[race condition](https://it.wikipedia.org/wiki/Race_condition)*).

## ⚠️ Synchronization Risks: [Deadlock](https://it.wikipedia.org/wiki/Deadlock) and [Starvation](https://it.wikipedia.org/wiki/Starvation_(informatica))

Managing **synchronization** and **resource waiting** can expose the system to two major problems:

### 🔄 Deadlock
A [**deadlock**](https://it.wikipedia.org/wiki/Deadlock) occurs when two or more processes **remain permanently blocked**, each waiting for a resource currently held by another process in the group.
* **Typical example**: Process `P1` **holds** resource `A` and requests `B`; process `P2` holds resource `B` and requests `A`. Neither can proceed.
* The system cannot recover from this blocking condition on its own; external intervention is required (such as restarting or forcibly terminating the processes).

### 🥶 Starvation
A [**starvation**](https://it.wikipedia.org/wiki/Starvation_(informatica)) occurs when a process **never manages to access** a resource because it is continually assigned to other processes (for example, due to **unbalanced priority policies**).
* Unlike deadlock, **it is not a permanent blocking condition**: the process is not permanently blocked, but must wait indefinitely until the allocation policy grants it access.

## 🏁 Summary

<KeyConcepts title="Key Concepts">
- [**Concurrency**](https://it.wikipedia.org/wiki/Concorrenza_(informatica)): execution of multiple processes during **overlapping time intervals**.
- [**Shared resource**](https://it.wikipedia.org/wiki/Concorrenza_(informatica)): a resource that can be used by multiple processes.
- [**Critical section**](https://it.wikipedia.org/wiki/Sezione_critica): a part of code that accesses a shared resource.
- [**Mutual exclusion**](https://it.wikipedia.org/wiki/Mutua_esclusione): allows only one process at a time to access a shared resource.
- [**Race condition**](https://it.wikipedia.org/wiki/Race_condition): a situation where the result depends on the order of concurrent operations.
- [**Deadlock**](https://it.wikipedia.org/wiki/Deadlock): processes block one another while waiting for resources held by the others.
- [**Starvation**](https://it.wikipedia.org/wiki/Starvation_(informatica)): a process waits indefinitely because it is not assigned a resource.
</KeyConcepts>

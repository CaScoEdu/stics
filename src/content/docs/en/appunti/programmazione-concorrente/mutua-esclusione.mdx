## Competition and Cooperation
When multiple [**processes**](https://en.wikipedia.org/wiki/Process_(computing)) run in a computer system, they can interact in two main ways:

* **Competition**: Two or more processes need exclusive use of limited **resources** that they both need, and therefore compete to acquire them. For example, two processes may try to write to the same file at the same time.
* **Cooperation**: Processes do not compete, but must **coordinate** and **exchange information** to perform a common task (e.g., a *producer* process that puts data into a [**buffer**](https://en.wikipedia.org/wiki/Data_buffer) and a *consumer* process that retrieves it).

In this lesson, we will focus on **competition**. **Cooperation** will be covered in a later lesson on the Producer–Consumer problem.

<Aside type="caution" title="The risk of disorder">
In both cases, a **lack of coordination** can cause **serious errors**,
**unpredictable behavior**, or **severe data corruption**.
</Aside>

## Competition: [Shared resource](https://en.wikipedia.org/wiki/Concurrency_(computer_science)), [critical section](https://en.wikipedia.org/wiki/Critical_section), and [mutual exclusion](https://en.wikipedia.org/wiki/Mutual_exclusion)
When processes **compete** for access to common elements (such as **global variables**, **files**, or **data structures**), any reusable hardware or software element contested by processes is called a **shared resource**.

<AsideNote title="Critical section">
To avoid **conflicts**, a **critical section** is the part of a process's code that accesses a shared resource to **read or modify it**.
</AsideNote>

### Why Mutual Exclusion Is Needed
To preserve **data consistency** and prevent [**race conditions**](https://en.wikipedia.org/wiki/Race_condition) (situations in which the execution order unpredictably changes the result), the system must guarantee [**mutual exclusion**](https://en.wikipedia.org/wiki/Mutual_exclusion):

<AsideCaution>
At any moment, at most **one process** can be in its **critical section** and use the **shared resource**.
</AsideCaution>

## The Access Protocol (Request – Use – Release)
To guarantee **mutual exclusion** and ensure that every process gains access in **finite time**, access to a resource must strictly follow a **standard protocol** consisting of three stages:

<Card>
<Steps>
1. **Request the resource**: The process requests exclusive access to the resource (if it is occupied, the process must wait).
2. **Use the resource**: The process enters the critical section and performs the required operations on the resource.
3. **Release the resource**: The process frees the resource, allowing other waiting processes to acquire it.
</Steps>
</Card>

## Practical Example: The [Stack](https://en.wikipedia.org/wiki/Stack_(abstract_data_type))

One classic **shared data structure** subject to competition is a **stack**, managed using an **array** and a **top pointer** (`top`).

Operations such as **push** (`Push`) and **pop** (`Pop`) modify the same **shared variables** (`stack[]` and `top`). If these operations run concurrently without proper **synchronization**, data may be **overwritten** or **undefined values** may be read (*[race condition](https://en.wikipedia.org/wiki/Race_condition)*).

## Summary

<KeyConcepts>
- [**Concurrency**](https://en.wikipedia.org/wiki/Concurrency_(computer_science)): execution of multiple processes during **overlapping time intervals**.
- [**Shared resource**](https://en.wikipedia.org/wiki/Concurrency_(computer_science)): a resource that can be used by multiple processes.
- [**Critical section**](https://en.wikipedia.org/wiki/Critical_section): part of code that accesses a shared resource.
- [**Mutual exclusion**](https://en.wikipedia.org/wiki/Mutual_exclusion): allows only one process at a time to access the shared resource.
- [**Race condition**](https://en.wikipedia.org/wiki/Race_condition): a situation in which the result depends on the order of concurrent operations.
</KeyConcepts>

## 🚦 Semaphores and the Integer Variable `S`
In 1968, [**Edsger W. Dijkstra**](https://en.wikipedia.org/wiki/Edsger_W._Dijkstra) proposed the use of two fundamental primitives to solve any problem of process interaction and synchronization: **`wait`** and **`signal`**.

These primitives operate on a **non-negative integer variable `S`** (called a *semaphore*):
- **`S = 0`**: red semaphore, meaning the resource is busy or unavailable.
- **`S > 0`**: green semaphore, meaning the resource is free or events are available.

:::note[The Mutex (Binary Semaphore)]
When the semaphore is used specifically for the **mutual exclusion** of a resource, it takes binary values (`0` or `1`) and is commonly called a **Mutex**. By convention, it is initialized to `1` by the operating system (resource initially free).
:::

## ⚙️ The `wait(S)` and `signal(S)` Primitives
To manage access to the shared resource `R`, processes invoke the two operations on the integer variable `S`:

* **`wait(S)`** (also called the acquisition operation): checks the state of `S`. If **`S < 1`**, the process blocks or waits. If **`S >= 1`**, the process decrements the variable (`S--`) and enters the **critical section**.
* **`signal(S)`** (also called the release operation): increments the semaphore variable (`S++`) to free the resource or wake any waiting processes.

## 🔒 The Classic Mutual Exclusion Protocol
To protect a shared resource and ensure that only one process can access it at a time, every process that intends to use it must strictly follow a standard protocol made of three sequential phases:
<Steps>
1. **Request for the resource (`wait`)**: the process invokes `wait(SR)` to test the semaphore state and acquire access.
2. **Use of the resource**: the process enters its **critical section** and performs the necessary operations on the shared resource `R`.
3. **Release of the resource (`signal`)**: at the end of operations, the process invokes `signal(SR)` to restore the free state and allow other waiting processes to proceed.
</Steps>
</StepCard>

## ⏳ Busy Waiting vs Passive Waiting
In the first theoretical implementations, `wait` was executed through a continuous loop (e.g. `while (S < 1) { }`), wasting CPU cycles (**busy waiting**).

In modern operating systems, waiting is handled **passively**:
<Steps>
1. A **waiting queue `Qs`** is associated with the semaphore.
2. If a process executes `wait(S)` and finds `S < 1`, the operating system **suspends** it, moving it from the *Running* state to the *Waiting* state and inserts its descriptor into the queue `Qs`.
3. When another process executes `signal(S)`, the system removes a process from the queue `Qs` and moves it to the *Ready* state, avoiding any waste of computing resources.
</Steps>
</StepCard>

## ⚛️ The Atomicity Problem in the Critical Section of `wait`
To understand how a semaphore works in depth, we need to analyze what happens internally during the `wait(S)` operation. Acquiring a resource through `wait` requires performing two distinct actions in sequence:
<Steps>
1. Check the semaphore state (verify whether `S >= 1`).
2. Update the semaphore (decrement it or suspend the process if `S < 1`).
</Steps>

### 🤔 What does "atomic execution" mean?
To avoid errors, these two operations must be executed in an **atomic** (indivisible) way. An atomic operation is a block of code that, once started by the processor, must run to completion without interruption and without any possibility that another process enters in the middle.

### 🤔 What would happen otherwise?
If the check and the subsequent update were not atomic, serious synchronization flaws could occur. Imagine this sequence with two concurrent processes (`P1` and `P2`) and a semaphore `S` initialized to `1`:

- Process `P1` checks and finds the semaphore free (`S = 1`). Before it has time to change it to `0` (busy), the operating system suspends `P1` and assigns the CPU to `P2`.
- Process `P2` also checks, finds the semaphore free (`S = 1`), and proceeds to occupy it.
- When `P1` resumes execution, convinced that the resource is free, it occupies it too.

The result is disastrous: both processes access the shared resource simultaneously, completely violating the principle of **mutual exclusion**.

### 🤔 How will we solve this problem?
In future hands-on exercises in concurrent programming in Java, we will see how the language provides native tools (such as the `synchronized` keyword or wait/notify blocks) that automatically manage this atomicity at the system level, protecting critical sections and preventing hidden conflicts among threads.
</StepCard>

<StepCard stepNumber="7">
## 🧩 Mutual Exclusion Scheme

Considering two concurrent processes `Q1` and `Q2` that access a resource `R` protected by a semaphore `SR` initialized to `1`, the structure of the code is as follows:

```javascript
// Initialization of the semaphore associated with the resource
SR = 1;

// Concurrent execution of processes Q1 and Q2
// --- Process Q1 ---
wait(SR);
  // === START OF CRITICAL SECTION (Use of R) ===
  // ... operations on the resource ...
  // === END OF CRITICAL SECTION ===
signal(SR);

// --- Process Q2 ---
wait(SR);
  // === START OF CRITICAL SECTION (Use of R) ===
  // ... operations on the resource ...
  // === END OF CRITICAL SECTION ===
signal(SR);
```
:::tip[Fundamental property]
While process `Q1` owns the resource (it has executed `wait` and has not yet executed `signal`), process `Q2`, which tries to access it, will find **`SR < 1`** and will be blocked, guaranteeing **mutual exclusion**.
:::
</StepCard>

<Aside type="note" title="Key Concepts Summary" icon="puzzle">
- [Semaphore](https://en.wikipedia.org/wiki/Semaphore_(programming)): synchronization variable that coordinates access to a resource or the availability of events.
- [`wait(S)` and `signal(S)`](https://en.wikipedia.org/wiki/Semaphore_(programming)): atomic operations used to acquire and release a resource by updating the semaphore value.
- [Mutex](https://en.wikipedia.org/wiki/Mutual_exclusion): binary semaphore used to guarantee exclusive access to a shared resource.
- [Critical section](https://en.wikipedia.org/wiki/Critical_section): part of code that accesses a shared resource and must be protected.
- [Mutual exclusion](https://en.wikipedia.org/wiki/Mutual_exclusion): property ensuring that only one process at a time can access the critical section.
- [Atomicity](https://en.wikipedia.org/wiki/Atomicity_(database_theory)): property that makes semaphore acquisition indivisible and prevents simultaneous access.
- [Busy waiting](https://en.wikipedia.org/wiki/Busy_waiting) and passive waiting: waiting modes based on repeated checking or suspending the process in a queue.
</Aside>

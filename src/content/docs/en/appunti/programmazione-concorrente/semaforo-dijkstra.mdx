## Semaphores and the Integer Variable `S`
In 1968, [**Edsger W. Dijkstra**](https://en.wikipedia.org/wiki/Edsger_W._Dijkstra) proposed using two fundamental primitives to solve problems of interaction and synchronization between processes: **`wait`** and **`signal`**.

These primitives operate on a **non-negative integer variable `S`** (called a [*semaphore*](https://en.wikipedia.org/wiki/Semaphore_(programming))):
- **`S = 0`**: red semaphore, meaning the resource is occupied or unavailable.
- **`S > 0`**: green semaphore, meaning the resource is free or events are available.

<AsideNote title="The mutex (binary semaphore)">
When a semaphore is used specifically to enforce [**mutual exclusion**](https://en.wikipedia.org/wiki/Mutual_exclusion) for a resource, it takes binary values (`0` or `1`) and is commonly called a **mutex**. By convention, the operating system initializes it to `1` (the resource is initially free).
</AsideNote>

## The `wait(S)` and `signal(S)` Primitives
To manage access to the shared resource `R`, processes invoke two operations on the integer variable `S`:

* **`wait(S)`** (also called the acquire operation): checks the state of `S`. If **`S < 1`**, the process blocks or waits. If **`S >= 1`**, the process decrements the variable (`S--`) and enters the [**critical section**](https://en.wikipedia.org/wiki/Critical_section).
* **`signal(S)`** (also called the release operation): increments the semaphore variable (`S++`) to free the resource or unblock any waiting processes.

## The Classic Mutual Exclusion Protocol
To protect a shared resource and ensure that only one process can access it at a time, every process that intends to use it must follow a standard protocol consisting of three sequential steps:
<Steps>
1. **Request the resource (`wait`)**: the process invokes the `wait(SR)` primitive to check the semaphore's state and acquire access.
2. **Use the resource**: the process enters its **critical section** and performs the necessary operations on the shared resource `R`.
3. **Release the resource (`signal`)**: once the operations are complete, the process invokes the `signal(SR)` primitive to restore the free state and allow any waiting processes to proceed.
</Steps>

## Busy Waiting vs Blocking
In early theoretical implementations, `wait` was performed using a continuous loop (e.g. `while (S < 1) { }`), wasting CPU cycles ([**busy waiting**](https://en.wikipedia.org/wiki/Busy_waiting)).

Modern operating systems handle waiting **passively**:
<Steps>
1. A **waiting queue `Qs`** is associated with the semaphore.
2. If a process executes `wait(S)` and finds `S < 1`, the operating system **suspends** it, moving it from the *Running* state to the *Waiting* state, and places its descriptor in queue `Qs`.
3. When another process executes `signal(S)`, the system removes a process from queue `Qs` and moves it to the *Ready* state, avoiding any waste of computing resources.
</Steps>

## The Atomicity Problem in `wait`'s Critical Section
To fully understand how a semaphore works, we need to examine what happens inside the `wait(S)` operation. Acquiring a resource through `wait` requires two distinct actions to be performed in sequence:
<Steps>
1. Check the semaphore's state (verify whether `S >= 1`).
2. Update the semaphore (decrement it or suspend the process if `S < 1`).
</Steps>

### What does "atomic" execution mean?
To avoid errors, these two operations must be performed **atomically** (or indivisibly). An atomic operation is a block of code that, once started by the processor, must run to completion without interruption or the possibility of another process stepping in midway.

### What would happen otherwise?
If the check and subsequent update were not atomic, serious synchronization failures could occur. Consider the following sequence with two concurrent processes (`P1` and `P2`) and a semaphore `S` initialized to `1`:

- Process `P1` checks the semaphore and finds it free (`S = 1`). Before it can change the value to `0` (occupied), the operating system suspends `P1` and assigns the CPU to `P2`.
- Process `P2` also checks the semaphore, finds it free (`S = 1`), and proceeds to occupy it.
- When `P1` resumes execution, believing the resource is free, it occupies it as well.

The result is disastrous: both processes access the shared resource simultaneously, completely violating the principle of **mutual exclusion**.

### How will we solve this problem?
In future practical exercises on concurrent programming in Java, we will see how the language provides built-in tools (such as the `synchronized` keyword or wait/notify blocks) that manage this atomicity at the system level, protecting critical sections and avoiding hidden conflicts between threads.

### Mutual Exclusion Structure

For two concurrent processes, `Q1` and `Q2`, accessing a resource `R` protected by a semaphore `SR` initialized to `1`, the code structure is as follows:

```javascript
// Initialize the semaphore associated with the resource
SR = 1;

// Concurrent execution of processes Q1 and Q2
// --- Process Q1 ---
wait(SR);
  // === START OF CRITICAL SECTION (Use of R) ===
  // ... operations on the resource ...
  // === END OF CRITICAL SECTION ===
signal(SR);

// --- Process Q2 ---
wait(SR);
  // === START OF CRITICAL SECTION (Use of R) ===
  // ... operations on the resource ...
  // === END OF CRITICAL SECTION ===
signal(SR);
```

<AsideNote title="Key property">
While process `Q1` holds the resource (it has executed `wait` and has not yet executed `signal`), process `Q2` will find **`SR < 1`** when it tries to access the resource and will be blocked, ensuring **mutual exclusion**.
</AsideNote>

## Summary

<KeyConcepts title="Key concepts">
- [Semaphore](https://en.wikipedia.org/wiki/Semaphore_(programming)): a synchronization variable representing the availability of a resource or an event.
- [Mutual exclusion](https://en.wikipedia.org/wiki/Mutual_exclusion): a property that allows only one process at a time to access a critical section.
- [Mutex](https://en.wikipedia.org/wiki/Mutual_exclusion): a binary semaphore initialized to `1`, used to protect a shared resource.
- [`wait(S)`](https://en.wikipedia.org/wiki/Semaphore_(programming)): an atomic operation that acquires the semaphore, decrementing it or blocking the process if it is unavailable.
- [`signal(S)`](https://en.wikipedia.org/wiki/Semaphore_(programming)): an atomic operation that releases the semaphore and increments its value.
- [Critical section](https://en.wikipedia.org/wiki/Critical_section): a section of code that accesses the resource protected by the semaphore.
- [Busy waiting and blocking](https://en.wikipedia.org/wiki/Busy_waiting): the process can repeatedly check the semaphore or be suspended in a waiting queue.
</KeyConcepts>
